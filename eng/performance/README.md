# Performance acceptance preparation

Reserve the shared machine before restoring, building, testing, or measuring. Use short, dedicated source, output and package-cache roots. Inspect planned output paths and package entry lengths before expansion. These runners do not install tools, clear shared caches, or choose performance thresholds.

## Matched released/candidate workloads

The released baseline is 2.2.0 at `b6e315db13a5b07ddd77696c9c0a5eefe6e9341f`. Overlay identical benchmark sources and `eng/performance` measurement helpers onto a separate baseline checkout. Keep baseline product sources unchanged. Use one exact SDK, Release configuration, workload profile and build arguments for both arms.

`Measure-CompilationStage.ps1` records one prepared `restore` or C# build interval. Supply an explicit `PreparedState`, relevant `InputPath` values, and the built harness as `OutputArtifact`. It records SDK, arguments, input hashes, artifact hashes, elapsed time, raw output and a build binlog. It never prepares or mutates source/cache state. Prepare a fresh copy for `first`, leave successful outputs for `no-change`, and make the declared body/schema/membership edit in that dedicated fixture before invoking the corresponding stage. C# build elapsed includes Generator work; it is not an isolated Generator duration. Cross-process allocation remains unavailable.

`Run-PerformanceMatrix.ps1` requires the exact SDK and those successful build receipts. It verifies the harness artifact, identical measurement sources and build arguments, alternates target order, and retains failed attempts. Fill in `matrix.example.json`; its SDK, build receipt and candidate SHA placeholders deliberately prevent accidental execution. The common Blog and typed Docs profiles measure `clean`, `warm-cache`, `no-op`, `single-page-change`, and `layout-change`. Warm cache loads persisted build state without an explicitly supplied previous plan; no-op supplies the previous plan. Neither means the operating-system file cache was cleared.

Typed Docs also exists in 2.2.0. Build that profile with `EnableTypedDocsBenchmark=true` on both arms to retain raw total-cost observations. Candidate Quality additionally retains raw HTML origins when Markdown source claims are admitted. Declare this difference in each target's `featureScope` and set `comparisonKind` to `feature-scope-difference`; this is not an equal-feature speed verdict. The matrix and curator do not calculate an automatic speedup or winner. Keep new component/schema/editor/codec acceptance work out of cross-version ratios. `GeneratorWorkload` remains a separate embedded Source **header-scan** substage, including reflection overhead, rather than full C# compilation or Generator throughput.

## Candidate-only acceptance costs

Build a separate harness output with `EnableMajorAcceptanceBenchmark=true`. This adds only the first-party Images project and uses `packages.acceptance.lock.json`, leaving the common harness lock graph separate. Generate and review that lock during the reserved restore phase. No candidate acceptance build or measurement has been executed merely by adding these sources.

Run `Measure-AcceptanceWorkloads.ps1` against that prebuilt DLL, with the exact selected SDK and a fresh evidence root. Select families and repetition counts before measuring:

- `editor`: initial, warm, unchanged, body, heading, reference-definition and large-paste inspection; fresh-result equivalence; after-close retained heap; cancellation of unclosed and deeply nested documents. The interval ends at `DocumentWorkspace` completion and excludes LSP transport and the editor UI.
- `yaml`: many small documents, long scalar, deep input, unknown metadata, typed binding and actual embedded Source YAML. Supply the built Generator assembly. The representative runtime/Source fixture checks values, diagnostics, spans and status outside the timed loop.
- `site`: initial, warm-cache, unchanged, body, layout, shared runtime binding/schema contract, and shared Markdown component. Loading/binding and generation durations are separate counters. This does not claim to measure a C# schema edit or Generator execution.
- Optional `factory`: explicitly provide `FactoryAssembly` and `FactoryDirectory` for the built official site's existing `GeneratedInputDirectory` hook. This measures factory creation, actual full-site initial/warm/unchanged generation, and post-disposal heap observations. It uses the real API page set instead of duplicating a synthetic fixed page count, keeps generated inputs/cache/output in the owned result directory, and records the live definition/catalog/previous-plan context. The harness's loaded Core is the measured implementation; package-consumer verification is a separate gate.
- `images`: PNG decode/encode, proportional resize, alpha composition, a site without images, opaque file copy, and a PNG asset transform miss/hit. Handler invocation checks confirm the cache state. Limited PNG and opaque copy are not equivalent to all former Skia features.

Pass explicit runtime, Source and Images package files or other distribution artifacts through `DistributionPath` to record bytes, hashes, archive entry counts, uncompressed bytes and longest entry names. An omitted distribution stage remains `not-executed`; harness deployment size is not a Core package footprint.

Raw samples, process output and failed attempts remain local. Managed bytes after forced collection are retained-heap observations; sampled working set is a separate measure. Candidate source-enabled Quality is explicitly labeled, including its global raw-fact cost for generated API HTML. Cancellation delay schedules the request, not a latency threshold. An operation that finishes before that request or fails to observe it is reported as such. Successful measurement execution remains `acceptance: not-evaluated`; compare fixed conditions, variation, correctness and unresolved regressions before making acceptance or speed claims. The MDX browser runner is maintained separately.
