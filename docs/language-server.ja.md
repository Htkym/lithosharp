# 言語サーバープロトコル

同梱の言語サーバーは Content-Length フレーミングを使い、stdio 上で LSP 3.17 を扱います。
位置の文字エンコーディングは UTF-16 です。

0.5.0 の VS Code 拡張は、Core 3.0.0 とともに、このサーバーを同梱します。
これは対象バージョンです。[バージョン一覧](../eng/version-matrix.json)では選定した開発候補と正式公開を区別します。
サーバーは別途インストールする NuGet ツールではありません。
DLL、ランタイム設定、依存関係をまとめて保持してください。[配布](distribution.ja.md)を参照してください。
Markdown の検査には、固定した Syntamark の runtime と Source の組み合わせ、および明示的に取得した Markdown プロファイルを使います。
MDX 本文の検査は明示的に復元する Node worker による別の経路です。

## 対応するプロトコルの範囲

広告する機能と、実装する機能は一致します。

- `initialize` / `initialized` / `shutdown` / `exit`。
- `textDocument/didOpen|didChange|didSave|didClose`。UTF-16 の増分同期です。
- `textDocument/publishDiagnostics`。push のみで、閉じる際はバージョンを付けません。
- `textDocument/documentSymbol`。Markdown の節の階層・範囲・見出し選択と、MDX の見出し範囲です。
- `textDocument/completion`。取得した独自フロントマターのフィールド、列挙型・真偽値の候補、登録した Markdown コンポーネントのメタデータです。
- `textDocument/hover`。取得した静的なフィールドとコンポーネントの説明です。
- `textDocument/definition|references`。取得した静的な Markdown の参照です。
- `textDocument/prepareRename|rename`。クライアントの機能が許す場合の、保護付きの見出し・参照編集です。
- `workspace/willRenameFiles`。合意した場合に、一度に一つの Markdown ファイルを移動します。
- `lithosharp/referenceScopes|previewRename` と `lithosharp/referenceStatus`。範囲の明示的な選択、プレビュー、利用可能性です。
- `$/cancelRequest`。処理中のシンボル、補完、ホバーの要求です。
- `lithosharp/projectContext`。クライアントが渡す、メジャーバージョンを検証するプロジェクトのスナップショットです。
- `lithosharp/analysisStatus`。文書・文脈の世代を付けた、解析の利用可能性のサーバー通知です。

ほかの要求には `-32601` を返し、ほかの通知は無視します。
stdout にはフレームだけを出し、ログはすべて stderr に出します。

初期化の応答は、`positionEncoding: "utf-16"`、増分テキスト同期、文書シンボル、補完、ホバー、定義、参照を広告します。
名前変更の機能はクライアントのバージョン付き編集と確認機能に応じます。
experimental の LithoSharp オブジェクトは、同梱する Core の識別情報、Markdown 検査、必要時の MDX 検査を報告します。
preflight の両フラグは false です。`preflight` は Tool のコマンドであり、LSP のメソッドではありません。
[機能の合意](tooling-capabilities.ja.md)を参照してください。

## 互換性の規則

- 未知のフィールドは無視し、未知のメソッドは拒否します。対応を推測しません。
- 位置のエンコーディングは常に UTF-16 です。列は UTF-16 コード単位で数え、Core では 1 始まり、LSP の境界の一か所だけで 0 始まりに変換します。
- 後退した文書バージョンと範囲外の編集は破棄し、stderr に記録します。異常な入力でも、サーバーは処理を続け、クラッシュしません。
- 互換性のないプロジェクトのアセンブリを読み込みません。文脈はスナップショットのデータであり、スキーマのメジャーバージョンの互換性を確認してから、ルート検索、組み込みバインド、明示的に取得した生成済み静的スキーマに使います。

## Markdown のシンボルと利用できない解析

Markdown のシンボルは診断と同じスナップショットを使います。
シンボルの `selectionRange` は元の見出し範囲、`range` は対応する節の `SubtreeSpan` です。
`HeadingLocalKey`、`LocalKey`、`ParentLocalKey` が、対応と階層を示します。
節の情報を利用できない場合は、既知の見出し範囲だけを保持します。
MDX は引き続き別の見出しベースの経路を使います。

入力やリソースの上限で、情報を利用できなくなる場合があります。診断は `LSM013` です。
信頼できるソース範囲がない場合は、文書の先頭に範囲を作らず、`lithosharp/analysisStatus` で状態を別に報告します。
後続の有効なスナップショットはその状態を解除します。
クライアントは、診断と同様に、古い文書バージョンとプロジェクト・文脈の世代を拒否する必要があります。
利用できない情報や部分的な情報は、文書が有効である根拠にはなりません。

状態のペイロードは、`uri`、`version`、`language`、`state`（`ready` または `unavailable`）、`message`、
`lithosharpOpenGeneration`、`lithosharpContextGeneration` を含みます。
診断も同じ open/context の世代を持ちます。
同じ URI を開き直すと、バージョンが同じでも新しいライフサイクルです。
MDX の依存関係がない場合も、ソース診断を作り出さずに、解析を利用できないと報告します。
worker の復元か設定の修正後に、サーバーを再起動してください。
`ready` は、文書にエラーがないことや、後続のビルド段階が実行されたことを意味しません。

新しいサーバーは、任意の `projectStatus`、`schemaName`、`schemaScope`、`projectId`、`projectGeneration`、
`projectHash`、スキーマ・入力のハッシュ、`contextAcquiredAt` も報告します。
プロジェクトの識別情報と取得時刻は、適用したスナップショットの説明であり、全入力が現在の状態である証明ではありません。
`projectStatus` は、Markdown 検査の文書の解決状態です。
`schemaScope` は `built-in-binding`、`static-schema-build-required`、`build-required`、`unknown` のいずれかです。
対応する検査経路を示し、バインドの成功を意味しません。
MDX は、組み込みスキーマの名前が文脈にあっても `unknown` を報告します。
これらのフィールドがない古いサーバーでは、対応する範囲は不明のままです。
VS Code 拡張は、診断と同じ識別情報の検証を使い、編集、文書の生存期間の変更、文脈の変更、サーバーの置換時に表示状態を無効にします。

`NoContext` では、構文診断と移動は利用できますが、プロジェクトに結び付くスキーマやルートの検査はできません。
明示的な Build または Inspect は、`IContentFrontMatterSchemaProvider` を実装するバインダーから、生成した `SchemaJson` を取得します。
独自のスナップショットは、スキーマバージョン `1.0`、プロジェクトの世代と取得ハッシュ、コレクションの識別情報、
スキーマのハッシュ、入力集合のハッシュ、正確な絶対パスの入力集合を含みます。
現在のスナップショットが一つだけ入力を対象とする場合に限り、スキーマを適用します。
ファイル名の接尾辞だけでは、入力集合に含まれる根拠になりません。不正なバージョン、ハッシュ、リビジョンの識別情報は拒否します。
新しい取得結果を拒否した場合、最後に分かっていたルートの根拠が残ることはありますが、
生成フィールドの候補、コンポーネント記述子、意味に関する情報は、有効な再取得まで破棄します。

独自フィールドの名前、null 許容、静的に必須の値、列挙型の候補、説明は、生成したメタデータから取得します。
静的検査は、ネイティブ YAML のキー・値・シーケンス項目の位置と、実行時と同じカルチャに依存しないスカラー変換を使います。
補完、ホバー、静的なスキーマ説明では、コンストラクター、ゲッター、セッター、初期化子に依存する要件、独自の検証処理を実行しません。
これらの制約はビルドが必要であり、静的スキーマの結果だけでは、実行時のバインド全体を保証しません。
宣言した意味の文脈でも、公開の判断が不明な場合は保留を維持します。

プロジェクトの選択、C# やプロジェクトの変更、入力の変更、新しい明示的な取得は、古い文脈を無効にします。
補完とホバーは、共通の解析を待つ間も、診断と同じバッファー・文脈の世代検証を使います。
プログラムから呼び出す場合は、生成した `SchemaJson` から `FrontMatterSchemaSnapshot` を作り、
`ProjectInspectionSnapshot.WithSchemas` で付加できます。取得ハッシュと正確な入力パスは、呼び出し側で渡す必要があります。

Markdown の節の情報とキーは、内部の連携用データです。
公開 `DocumentInfo` の追加プロパティや、MDX が Markdown の節を使う保証ではありません。
同じスナップショットのシンボルと診断は、サーバーが所有する作業を共有します。
シンボル、補完、ホバーの要求のキャンセルは、その待機側を取り消し、共有する診断解析は取り消しません。

## 参照先への移動と保護付きの編集

参照の要求には、開いた Markdown 文書と、明示的に取得した曖昧でないプロジェクト入力の範囲が必要です。
定義と参照の検索は、解析したネイティブの参照情報と取得済みのルートを使います。
`lithosharp/referenceScopes` は、利用できるコレクション・バージョン・言語の範囲を列挙します。
入力に複数の範囲がある場合は、`referenceScope` を渡してください。
動的な MDX と閉じたファイルは、手動確認または利用できない範囲として明示し、完全な参照検索の根拠にはしません。

`lithosharp/previewRename` は、適用せずに、保護付きの編集、手動確認の範囲、文書・ハッシュの識別情報、現在の利用可能性を返します。
見出しの編集、参照先の変更、一つのファイルの移動は、現在の取得済みバッファーで再検証する必要があります。
参照範囲が不明または不完全な場合は、参照先の不在を証明できません。
任意の `expectedSourceTextHash` と文書バージョンは古い要求を拒否します。

自動編集には、バージョン付きの `documentChanges` が必要です。
広告する名前変更の経路には、確認用の注釈も必要です。
複数ファイルにまたがる編集には、`transactional` または `textOnlyTransactional` の失敗処理が必要です。
リソースの移動は別に合意し、一度に一つの `.md` ファイルを受け付けます。
未対応のクライアントには、バージョンのない編集を返さず、明示的なプレビュー経路を残します。
`lithosharp/referenceStatus` は、残る手動確認の範囲と、取得した文書・文脈の世代を報告します。
C# の呼び出し側の変更には、別の [C# 参照の名前変更プレビュー](csharp-reference-rename.ja.md)が必要です。
Markdown のプレビューは、再生成する C# メタデータや、すべての後続の呼び出し側の正しさを証明しません。
