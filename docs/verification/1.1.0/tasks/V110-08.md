## 棚卸し（手順1）

| 保持物 | 分類 | 所有者/key | 上限 | 破棄契機 |
| --- | --- | --- | --- | --- |
| `SiteBuildCache` の builds/blobs/parses | disk | 出力ごとの partition（`<cacheRoot>/<outputIdentity>`）、keyは内容hash | なし（蓄積する） | なし（従来は手動削除のみ） |
| MDX bridge cache `<cacheDir>/mdx/<signature>.json` | disk | cache root 共有、keyは pages+toolchain+options+BuildTimestamp | なし（1 build 1ファイル、assetsのbase64込み） | なし（同上） |
| MDX scratch `work-*` / `*.tmp` | disk | 1リクエスト | — | 正常系は finally、強制終了時は残留 |
| worker `moduleCache` / `renderCache` | process-global | worker内、entry数上限（2048〜20000） | あり（FIFO、byte予算なし） | worker終了 |

| `DocumentWorkspace` snapshots | per-project | `_snapshots` | 呼び出し側の Remove/Dispose | `DisposeAsync` |
| 秘密値 | — | `MdxOptions.Environment` は worker 起動環境のみ、署名はhash、inspectionは公開propsのみ | — | — |

- 元source・秘密値は cache に平文で残らない。disk cache は世代を消さない設計（壊れた/未知の entry は
  読み捨てて再構築するが、ファイルは残る）。

## 実装

1. **可視化と明示清掃**（手順3）
   - `SiteGenerator.MeasureCache(outputRoot, options?)` / `ClearCache(outputRoot, options?)` を追加し、
     `SiteBuildCacheUsage`（CacheDirectory / FileCount / TotalBytes）を返す。出力識別子は生成側と同じ
     `CreateOwnershipScope` / `CreateOutputIdentity` を使うため、**その出力の partition だけ**が対象になる
     （他出力・公開treeは触らない）。
   - CLI `lithosharp cache <info|clean> -o <directory> [--cache-dir <directory>]` を追加。ビルドからは
     独立した明示実行で、`clean` が cache を消さない現行仕様は維持する。
   - 実データ確認：V110-07 の 100頁 MDX ビルドの partition を 103ファイル / 2,170,733 bytes と検出し、
     clean で削除、再 info で 0 を確認（識別子計算が生成側と一致していることも確認できた）。
2. **クラッシュ残骸の回収**（手順5/7）：`MdxSite.PrepareAsync` が `<cacheDir>/mdx` の `work-*` と `*.tmp` の
   うち1日より古いものだけを削除する。生存ビルド（1日未満）は触らない。
3. **壊れたcache読み取りの分離**（手順4）：MDX bridge cache の読み込み catch に
    `UnauthorizedAccessException` を追加し、permission 拒否を miss として再構築する。`SiteBuildCache` の
    読み取りは既に `IsCacheReadFailure` で縮退済み。書き込み失敗時の扱いは2026-10-03レビュー追記を参照。

## 残り（V110-24/25へ）

- worker `moduleCache` / `renderCache` の byte 予算 LRU（現状は entry 数 FIFO。`compiler.mjs` のコメントどおり）。
- MDX bridge cache は `BuildTimestamp` を署名に含むため、既定（UtcNow）では毎ビルド1ファイル増える。
  自動削除は計画の禁止事項なので、`cache clean` による明示回収のみ（可視化は今回実装）。
- 計測（手順6）：working set / managed heap / Node heap / handle / cache bytes の時系列は
  `Test-MdxWatch.ps1` と `DocumentWorkspaceTests` が部分的。cache bytes の時系列と soak 連携は V110-24/25。
- watch overflow、dispose 競合、cancel 後の同一 `MdxSite` 再利用の専用テストは未追加（V110-25）。
- 既存 `SiteBuildCache` にも prune API は付けていない（`cache clean` が partition 単位で代替）。

## 2026-10-03 全改修レビューの追記

- `MeasureCache` / `ClearCache` は生成と同じper-output lockを取得する。実行中buildのcacheを列挙・削除せず、reparse pointを含むpartitionは再帰処理しない。
- `SiteBuildCache` のbody/parse/build record書込みとMDX bridge cache保存はbest effortに変更した。任意cacheへ書けなくても、現在のbuildはメモリ内の結果で続行し、出力manifestはcache keyなしで公開する。必須の出力・asset書込み失敗は引き続きbuildを失敗させる。
- MDX stale-scratch回収はwork directoryとその配下のreparse pointを拒否してから削除する。cleanup失敗はbuildを止めない。
- regression coverage: `UnavailableOptionalCacheDoesNotFailTheBuild` と `ClearCacheWaitsForAnActiveBuildOfTheSameOutput`。
