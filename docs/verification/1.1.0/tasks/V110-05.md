## 何をしたか

1. **段階カウンタを加算APIとして製品に追加**した（環境に依存しない帰属のため）。
   - `SiteGenerationOptions.CollectTimings`（既定 false、無効時は結果が `null`）
   - `SiteBuildTimings`（`Plan` / `Transaction` / `CacheLoad` / `Execution` / `Verification` / `Quality` / `Commit` / `Total` のミリ秒と `VerifiedArtifactCount`）
   - `SiteGenerationResult.Timings`（加算、既存の等値契約は不変）
   - 併せてmarkdown benchmarkが`CollectTimings`を有効化し、結果JSONへ段階値を含める。
2. **計測に基づき入力経路の重複を調査**した。no-op/本文1件で支配的なのは既存出力のstaging複製で、入力走査・fingerprint・計画は小さい（下表）。したがって入力経路の追加最適化は行わず、根拠を記録した。
3. **必須テストの欠落を補った**：`SourceFileEditWithSameLengthAndTimestamp_IsReread`（同サイズ・同mtimeの編集を内容hashで検出）。`MarkdownPostReader`/`MarkdownContentCollectionLoader`にmtime・length依存の短絡が無いことも確認した。

## 計測（1,000頁、同日・同条件、ms）

| 段階 | no-op | 本文1件 |
| --- | --- | --- |
| Plan（入力正規化・計画構築） | 171 | 145 |
| Transaction（既存出力のstaging複製） | 7,210 | 11,650 |
| CacheLoad | 72 | 76 |
| Execution（key計算・検証・描画・書込） | 472 | 1,248 |
| └ うち Verification（成果物の読取+hash） | 13 | 44 |
| Quality（検査・manifest・所有権準備） | 282 | 364 |
| Commit | 824 | 738 |
| Total | 9,038 | 14,227 |

- 入力・fingerprint・計画（Plan＋CacheLoad＋Execution＋Verification）は no-op で **約0.7s / 9.0s（8%）**、本文1件で約1.5s / 14.2s（11%）。
- **支配的なのは出力staging（Transaction＋Commit）で no-op 89%、本文1件 87%**。これは設計どおりの atomic publication（公開中のtreeを部分上書きしない）のコストで、V110-06（派生成果物・出力stagingの改善）の対象。
- Verificationが13〜44msと小さいのは、直前に複製したばかりでOS page cacheに載っているため。成果物の完全hash検証は維持する（外部改変・欠落の検出は必須）。
- 環境は依然として低速（昨日のno-op 5.8s → 本日9.0s）だが、段階比は決定的で環境差の影響を受けにくい。
