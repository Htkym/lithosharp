実施日：2026-09-24（日本時間）

## 確認したこと（計測）

V110-05 の段階カウンタで、1,000頁の no-op / 本文1件はいずれも**出力staging（Transaction＋Commit）が支配**と判明していた。本タスクで追加確認した点：

- Transaction は `OutputTransaction.CreateAsync(preserveExisting: true)` 内の `CopyDirectoryAsync`（公開中の全成果物をstagingへ複製）で、1,012ファイルあたり 7.2〜15.8秒。同数のコピーを `Copy-Item` で行うと約2.3秒なので、製品側の per-file 処理（reparse検査・final path検査・metadata capture/restore）が支配的。
- 検索・派生物については、V110-05の段階値で Quality（検査・manifest・所有権）が 173〜364ms、Execution（cache判定・key・検証・描画）が 188〜1,248ms に収まっており、本タスクが対象とする「全成果物の処理増幅」は staging に集中している。検索indexの公開formatは不変（byte determinism はテストで維持）。

## 実験：ファイルコピーの並列化

- `CopyDirectoryAsync` のファイル複製のみを `Parallel.ForEachAsync`（2〜8並列）にし、ディレクトリmetadataの列挙順（commit時に深い順で適用）は維持した。
- HEAD（ac05526）の harness を別 worktree でビルドし、交互A/Bで `transactionMilliseconds` を比較：
  - pair1: before 9,491ms / after 10,208ms
  - pair2: before 15,799ms / after 7,482ms
  - 同一コード（before）が 9.5s → 15.8s と 66% 変動し、2 pairでは判定不能。
- 計画書の「profilingで効果が確認された変更だけ採用する」「効果のない複雑化を採用しない」に従い、**この変更はrevertした**（rawは証跡に保持）。

## 次段の設計（実装候補）— 実装手順まで確定

未変更成果物の複製をやめる **overlay方式**を第一候補とする。実装は次の順で行う（各段でビルドとテストを通す）。

1. **OutputTransaction の複製を遅延化**（挙動不変）
   - `CreateAsync` に `deferExistingCopy` を追加し、`_preserveExisting` と `_existingOutputCopied` を保持。
   - `MaterializeExistingOutputCopyAsync(cancellationToken)` を追加（冪等、既存の `CopyDirectoryAsync` を呼ぶだけ）。
   - 既定は従来どおり即時複製（`deferExistingCopy: false`）。
2. **bypass 判定を `ExecuteBuildAsync` に追加**
   - 条件：`!clean`、`subset` でない、`assets.ExecutedTransformNodes` が空、`cachePolicy=always-rebuild` のノードが無い、全ノードで `previous.NodeKey == 現在key` かつ artifact 宣言が一致、stale所有物が無い、previous所有権状態が存在。
   - 成立時は複製せず、公開中の成果物を `PublishedRoot` でその場検証する。
   - 検証失敗時は `MaterializeExistingOutputCopyAsync` を呼び、`bypass=false` にして従来の miss 経路へ戻す（安全側）。
3. **caller 側の分岐**：bypass 時は `WriteOutputManifestAsync`／`PrepareOwnershipStateAsync`／`CommitAsync`／`cache.SaveAsync` をスキップ（内容が同一のため書き換え不要）。品質検査の読み取りrootは `outputRoot`、`GeneratedFiles` は plan の artifact から outputRoot 基準で構築。
4. **テスト**：既存の `SiteGeneratorAtomicOutputTests`（stale削除・失敗保持・read-only・cancel・旧出力hash）に加え、bypass 後に (a) 公開treeのbyte hashが不変、(b) 出力の1ファイル改変で bypass が無効化され再生成される、(c) 所有権状態・manifestが不変、を assert する新規テスト。
5. **計測**：静かな環境で **5 pair以上の交互A/B**（before/after交互、中央値とraw保存）。対象は1,000頁の no-op と本文1件。期待は Transaction 7.2〜15.8s → 0.1〜1s（検証のread+hashのみ）。環境変動が ±10% を超える場合は run を増やす。


1. cache判定の結果、全ノードがhitで、stale削除が無く、subsetでない場合、stagingの複製を作らず、公開中の成果物を**その場で読み取り+hash検証**する（現行の所有権状態のhashと照合）。2. 品質検査は公開中のtext成果物を読む（検査条件は同一）。
3. commitは「変更なし」として公開treeを書き換えず、manifest・所有権状態も再書き込みしない。
4. 本文1件変更などstagingが必要な場合は、変更/削除対象だけをstagingへmaterializeし、commitでバックアップ+rollback付きのoverlay公開を行う。

制約（計画書の必須条件）：atomic publicationを維持、所有権検査とfailure rollbackを省略しない、共有hardlinkへ書き込まない、manifest/所有権状態の整合を保つ、`SiteGeneratorAtomicOutputTests` のstale削除・失敗保持・read-only・cancel・旧出力hashの各テストを維持する。

検証手順（必須）：静かな環境で **5 pair以上の交互A/B**（before/afterを交互実行し中央値とrawを保存）。今回は環境変動が ±66% あり、2 pairでは判定できなかった。V110-25の最終認定ではこの手順を前提とする。
