# V110-07 — MDXの増分compile/render/bundleとworkerを改善する

実施日：2026-09-24（日本時間）
状態：VERIFIED（entry単位のrebundle counterを実装し、宣言済みの3つのscenario gapをgateとテストで閉じた）
対象成果物：Mdx
証跡：`.local/verification/1.1.0/v110-07-20260924/`（size 100 scenario実行の measurements.json、テストログ）

## 現状の確定（手順1）

増分は「workerは保持するがesbuildはサイト全体で1回」だった。

- compile：worker内 `moduleCache` でモジュール単位に増分（変更分のみ再compile）。`compiledModules` で実測できる。
- render：worker内 `renderCache`（server chunk bytes + selectiveフラグ）でページ単位に増分。`renderedPages` で実測できる。
- bundle：server/browser とも esbuild の `build()` を1回だけ呼び、全entryと全style entryを毎回再生成する。
  ただし entry/chunk 名に content hash が入るため、依存closureが同じ entry は出力パスもバイトも不変で、
  .NET側の asset node も再利用される（ファイルの書き換えは起きない）。
- 「本当に変わった entry が何件か」を数える counter は無かった（`scenarios.json` の gap 記録どおり）。

## 実装

- `worker/compiler.mjs`：ブラウザ出力の署名（entry の imports closure + stylesheet closure の、
  内容hash入りパス集合）をページ単位で前回リクエストと比較し、`rebundledPages`（変わった interactive entry の
  page id）を返す。プロセス内 `browserSignatures` に保持し、worker 再起動後は全 entry が対象になる（保守的）。
- `MdxBuildMetrics.RebundledPages` / `RebundledPageIds` を追加（`PublicAPI.Unshipped.txt` 登録）。
  disk cache hit 時は 0 / 空（workerを呼んでいないため）。
- harness `LithoSharp.MdxPerformance` の gate を追加：
  - `one-page`（静的本文1件変更）：`RebundledPages == 0`、`CompiledModules == 1`、`RenderedPages == 1`、cacheMiss<=5
  - `shared-component` / `shared-css`：`RebundledPages > 0`（依存 entry が再bundleされる）
- 計測 runner の counter 名を修正：`bundledEntries`（実在しない）→ `bundledPages`、`rebundledPages` を追加。
  これまで ledger に `bundledEntries: null` が記録されていた。

## 実測（size 100、scenarioごとに独立プロセス、ms）

| scenario | compiled | rendered | bundled | rebundled | worker | server bundle | browser bundle | elapsed |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| prepare（cold） | 100 | 100 | 20 | 20 | — | — | — | 7,231 |
| one-page（静的本文） | 1 | 1 | 20 | **0** | 2,153 | 762 | 546 | 5,045 |
| shared-component | 0 | 20 | 20 | **20** | 1,712 | 523 | 348 | 4,736 |
| shared-css | 0 | 0 | 20 | **20** | 2,410 | 735 | 444 | 6,008 |

- 静的本文1件の変更では interactive entry は1つも変わらない（entry/byte単位で0）。.NET側の cacheMiss も1件。
- shared component / CSS の変更では、依存する全 entry（この corpus では20件）が更新される。
- cold build は全 entry が新規なので rebundled = bundled = 20（この定義を test で固定した）。

## 判断と残り

- **全entryのesbuild呼び出しは残した**。browser build は `splitting: true` で共有 chunk を entry 間で共有しており、
  entry ごとに分割して呼ぶと共有 chunk が複製される（出力増）。増分 bundle には esbuild の `context()/rebuild()`
  か共有 chunk 込みの closure cache が必要で、byte 単位の再生成はすでに起きていない（再公開0）ため、
  このtaskでは counter と gate の確立を優先した。browser bundle は 0.35〜0.55s（size 100）で支配要因ではない。
- **cache key は変更なし**。既存 signature は全 page 本文・toolchain（worker 全ファイル + node_modules）・
  resolution 候補（project 全ファイル、package.json 等は内容hash）・options を含み、disk cache hit 時は
  worker が報告した全 input を再hash検証する。依存 closure は保守的に含まれている。
- 残り（V110-08/25）：段階別 profile の深掘り、10,000頁での再確認、module cycle と import rename/delete の
  専用テスト（現状は壊れた import の出力保持テスト、worker テスト、watch e2e で部分的にカバー）。
