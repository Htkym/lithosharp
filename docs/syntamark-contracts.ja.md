# LithoSharp で使う Syntamark の契約

[English](syntamark-contracts.md)

LithoSharp は固定した Syntamark runtime と Source の組み合わせを使います。
選択したバージョンと公開の状態は、[バージョン一覧](../eng/version-matrix.json)に記録しています。
runtime は公開解析 API を提供し、Source はコンパイラーホストへ移植可能なパーサーを組み込みます。
Source は runtime の公開 API をもう一式提供するパッケージではありません。
バージョンを混在させたり、名前が同じという理由だけで Source を置き換えたりしないでください。
単独で使う場合の API 全体と導入方法は、[Syntamark のリポジトリ](https://github.com/Htkym/syntamark)で説明します。

## プロファイルと描画

LithoSharp の既定値は引き続き `lithosharp-markdown/1` です。
`commonmark/0.31.2` と `syntamark-docs/2` は明示的に選びます。
文書用プロファイルはネイティブの脚注とディレクティブの構文を有効にします。
HTML の描画、見出しのスラッグ、ルート、登録した型付きコンポーネントの実行は、LithoSharp が担当します。
パーサーの解析情報は実行可能な式や任意の利用者コンポーネントを許可するものではありません。
MDX は別の信頼する worker を使います。
[プロファイル](markdown-profiles.ja.md)、[MDX](mdx.ja.md)、[型付きコンポーネント](typed-markdown-collections.ja.md)を参照してください。

## 原文の位置と選択解析

scope、ソースの識別情報、ソースのバージョン、テキストのハッシュ、オプションのハッシュ、
プロファイル、パーサーの契約で入力を識別します。
原文の位置は BOM と元の改行を含む UTF-16 コード単位で数えます。
入力を正規化したうえで、その位置を別の文字列に適用してはいけません。
組み込みコンパイラーが使う portable の `Blocks` 出力は本文からの相対位置です。
runtime の公開 AST をもう一式提供するものではありません。
公開解析情報、未対応構文の候補、編集範囲は、元の入力全体を参照します。
include と原文のマッピングは、それぞれの精度と関連する出典を保持します。
精度が不明な位置に、行番号を推測して付けません。

`MarkdownParser.Analyze` と `MarkdownParser.CreateAnalysisSession` では
`MarkdownAnalysisParts` を指定します。
`All` には `UnsupportedSyntax` が含まれないため、候補の診断にはこのフラグも明示します。
null の場合がある出力を読む前に、`Status` と各項目の `GetAvailability` を確認してください。
`GetAvailability` は項目を一つずつ指定する API で、`None`、`AllFacts`、`All` は受け付けません。
`NotRequested`、`Partial`、`Unavailable` は、取得が完了して結果が空である状態とは異なります。
未対応構文、リソースの上限、キャンセルから、文書全体の妥当性は証明できません。
front matter の走査はヘッダーの境界を読みますが、本文全体の解析を保証しません。
[診断](diagnostics.ja.md)と[言語サーバーの文脈取得](language-server.ja.md)を参照してください。

## 増分セッション

セッションは不変で、明示的に使う機能です。
`ApplyEdits` は、直前の入力の UTF-16 座標に基づく、整列した重複のない編集を受け取り、期待するテキストのハッシュを確認します。
新しいセッションを返し、失敗やキャンセルの場合は、以前のセッションを保持します。
`Mode` と `Fallback` は実際に通った経路を示します。
再利用・位置を調整したブロック数と `ParsedBlocks` は、ブロックの再利用を表します。
`ParsedBlocks` が数えるのは対象となる通常の段落で、すべてのブロックや解析情報の生成ではありません。
`ScanUnits` は再実行分を含む通常のパーサーの論理的な走査量で、実際の処理量や所要時間の測定値ではありません。
通常の完全解析への切り替えも対応する経路であり、差分処理の成功を示すものではありません。
オプションが null の場合は、以前のセッションのオプションを維持します。

文書の解析と変換済みの Markdown 本文には、テキスト、オプション、識別情報を分けたセッションが必要です。
LithoSharp が保持した本文解析を使うには、要求した項目と本文入力のオプションも一致し、`SourceVersion` が null である必要があります。
元の文書のバージョンが付いた結果を、この本文の結果として使うことはできません。
エディターはプロトコルの変更を受け取った順に適用し、古い世代の結果を抑止します。
選択解析そのものは増分セッションではありません。
パーサーの再利用とは別の描画キャッシュ、診断、依存関係は、[増分ビルド](incremental-builds.ja.md)を参照してください。

## YAML・脚注・校正

共通の YAML 構文木は原文と未知の値を保持します。
文書に記載した上限の範囲で、ブロック形式とフロー形式のマッピング・シーケンス、
プレーン形式と引用形式のスカラー、リテラル形式と折り畳み形式のブロックスカラーに対応します。
タグ、ディレクティブ、アンカー、エイリアス、複雑なキーには対応しません。
構文の誤りとリソースの上限はそれぞれ別の種類の診断を返し、暗黙に正常な完全構文木へ変換しません。
型付き DTO バインダーが対応するのは、文書に記載したマッピングの範囲です。
構文木を、制約のないシリアライザーへ変えるものではありません。
対応する DTO の契約は[型付き YAML](typed-yaml-collections.ja.md)と[移行](migration-3.0.ja.md)を参照してください。
OKF は独自の適合ポリシーを使い、DTO のバインドとは別に、未知の入力と原文を保持します。

文書用プロファイルは同じスナップショットから脚注の定義と参照を解決します。
ほかのプロファイルは従来どおりリテラルとして扱います。
呼び出し側は重複する定義、未解決の使用箇所、元のラベルを取得できます。
LithoSharp は別の Markdown 字句解析器を追加せず、解決した番号と戻りリンクを描画します。

校正は明示的なテキスト領域と原文のマッピングを使います。
解析中にリモートのモデルを実行せず、解析が完了したという理由だけで提案を適用することもありません。
CLI で校正を実行するには明示的な操作が必要です。
編集のプレビューを返すことはできますが、ファイルへの書き戻しは行いません。
適用可能な編集には、ネイティブ解析による正確な範囲が必要です。
行だけを示す指摘の精度は最大でも `CoveringTokens` であり、自動置換を許可するものではありません。
API の `Apply` を明示的に呼ぶと、ソースの識別情報、バージョン、テキストのハッシュ、期待する原文を確認し、新しい文字列を返します。
この API もファイルへの書き込みは行いません。
[校正](proofreading.ja.md)、[参照の編集](reference-editing.ja.md)、[既知の制約](known-limitations.ja.md)を参照してください。
