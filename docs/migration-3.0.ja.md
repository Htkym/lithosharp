# LithoSharp 3 への移行

LithoSharp 3 は固定した Syntamark 2 の runtime と Source の組み合わせを使って開発しています。
[バージョン一覧](../eng/version-matrix.json)では選定した候補とリリース予定のバージョンを分けています。
候補パッケージを利用し、ローカルで検証しただけでは、正式に公開されたことにはなりません。

既存のサイトと公開済みの出力を保持し、新しい出力先で移行を試してください。
公開に成功した時点の出力から取得した基準と、公開 URL やアンカーを比較します。
ビルドはこの基準を更新しません。

## ネイティブ YAML とコンテンツ属性

アプリケーションがほかの用途で YamlDotNet を使っていなければ、直接の依存関係を削除します。
`YamlMember(Alias = "name")` を `ContentName("name")` に、`YamlIgnore` を `ContentIgnore` に置き換えます。
どちらも `LithoSharp.Content` にあります。既定のメンバー名は snake_case です。
名前は NFC に正規化され、正規化後に衝突する名前は拒否されます。

ネイティブ YAML リーダーが対応するのは、文書に記載した YAML の一部です。
YamlDotNet が受け付けるすべての機能には対応していません。
アンカー、エイリアス、タグ、マージキー、複雑なキー、複数の文書は拒否されます。
構文エラー、未対応の機能、リソース上限は、それぞれ異なる診断として扱われます。
部分的な解析結果は有効な型付きマッピングを証明しません。
実行時とコンパイル時の型付きコンテンツリーダーでは、入れ子の深さの上限を 64 に統一しています。
独立したネイティブ文書 API には、固有のオプションがあります。

`MarkdownFrontMatterYaml.Deserialize<T>` は、コンテンツコレクションと同じ厳密なバインダーで DTO のマッピングを読みます。
対応する DTO と、公開された引数なしコンストラクターが必要です。
このヘルパーは、ルートがスカラー、シーケンス、辞書、型を指定しないオブジェクトの場合には対応しません。
構文ノードや制約の緩いメタデータ表示が必要な場合は、Syntamark のネイティブ YAML 文書 API を使ってください。
投稿専用の `Deserialize(string)` ヘルパーでは未知のフィールドに対する従来の動作を維持します。

`MarkdownFrontMatterYaml.Serialize(PostFrontMatter)` は、文字列を引用符で囲み、決定的な新しいメタデータを書き出します。
既存の YAML 文書の書式や元のバイト列は保持しません。
OKF の保持エクスポートと元のバイト列の保存は、別の操作です。

## Core の画像参照と任意の PNG 処理

Core は SkiaSharp やネイティブ画像ライブラリをインストールしません。
既存のアセットを登録し、URL、寸法、レスポンシブ画像のバリアントを明示します。
Core は、寸法を取得するために画像をデコードしたり、不足する形式を生成したりしません。
記述子が要求する箇所には、フォールバック用のバリアントと寸法を指定してください。
詳しくは[アセットと画像](assets-and-images.ja.md)を参照してください。

`LithoSharp.Images` は、任意で追加する PNG 処理パッケージです。
初期のコーデックは、明示したリソース上限の範囲で、8 ビットかつ非インターレースのグレースケール、RGB、
グレースケールとアルファ、RGBA の PNG 入力に対応します。
パレット形式、インターレース、ほかのビット深度の入力は、この処理に渡す前に変換が必要です。
JPEG、WebP、AVIF のバリアントは既存ファイルとして登録できますが、このパッケージはそれらをエンコードしません。

暗黙のソーシャル画像生成を、`CommonSocialImage`、出力ごとの `SocialImages`、
または明示的に登録した `SocialImageAsset` に置き換えます。
任意の PNG 合成機能は宣言された画素とロゴを組み合わせます。
従来のフォントによる文字描画や、外部の AVIF プロセスを使うフォールバックは提供しません。

## Markdown プロファイルと型付きコンポーネント

既定のプロファイルは引き続き `lithosharp-markdown/1` です。
`commonmark/0.31.2` または `syntamark-docs/2` は、`SiteGenerationOptions.Markdown` で明示的に選択します。
フロントマターのバインドと文書の公開ポリシーは、この選択とは別です。
プロファイルを変えると、互換性のある解析キャッシュと描画キャッシュが無効になります。
公開前に、見出し、アンカー、拡張構文、HTML の変化を確認してください。

文書用プロファイルでは構造化されたコンポーネント属性と脚注を使えます。
型付きコンポーネントを明示的に登録し、設定の識別情報と、依存するファイル、値、アセットを宣言します。
コンポーネント属性はリテラル値であり、C# の式を評価しません。
参照ルールには、現在の文書の識別情報と、十分なカタログの根拠が必要です。
不完全な文脈からは参照先の存在も不在も証明できません。

## 静的入力とエディターの根拠

生成されたカタログの入力集合とルートを利用するには、明示した入力ルートとともに
`MarkdownContentCollectionLoader<T>.FromCatalog` を使います。
従来のローダーのコンストラクターも引き続き使えます。
静的入力の追加、欠落、移動があった場合は、カタログの再ビルドが必要です。
物理パスの表記は保持し、識別情報の比較では Unicode を正規化して衝突を拒否します。

エディター用スキーマは、信頼したプロジェクトを明示的に検査またはビルドして取得します。
入力中に、利用者のコンストラクター、セッター、検証デリゲート、コンポーネントは実行しません。
静的なスキーマ検証、カタログに依存するルール、ビルドが必要な検査は、異なる根拠を使います。
スキーマや入力集合の構成が変わると、取得済みの根拠は無効になります。

## キャッシュされた成果物と検証記録

画像変換のメタデータと、コレクションの診断キャッシュの形式が変わりました。
互換性のない記録はキャッシュミスとして扱います。
診断結果の欠落は不明な状態であり、診断なしで検証に成功した状態ではありません。

翻訳レビュー記録は原文と翻訳の正確なリビジョンを識別します。ビルドは記録を更新しません。
スニペット検証で実行するのは、明示的に対応付けた、信頼したプロジェクトとテストだけです。
入力が変わると、以前の成功は無効になります。
テストプロセスが正常終了しても、テスト実行の根拠がなければ、スニペットを検証したことにはなりません。
これらの結果は、OKF の信頼性に関する証明記録を作成せず、文書の技術的な正しさも証明しません。
