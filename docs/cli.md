# CLI and site factories

`LithoSharp.Tool` is a .NET 10 tool. Building sites requires the .NET 10 SDK
(10.0.300 or later);
serving also uses the ASP.NET Core shared framework. Install from NuGet:

```powershell
dotnet tool install LithoSharp.Tool --version 2.2.0 --tool-path .tools
dotnet new install LithoSharp.ProjectTemplates::2.2.0
.tools/lithosharp new docs MyDocs -o MyDocs
.tools/lithosharp build MyDocs
.tools/lithosharp serve MyDocs
```

The template package is separate from the tool. Its short names are
`lithosharp-docs`, `lithosharp-blog`, `lithosharp-empty`, and `lithosharp-mdx`; they also work directly
with `dotnet new`. The empty template demonstrates a custom C# layout.

## Inspection and migration

The installation example targets 2.2.0. `preflight` and `migrate testing --dry-run` are part of the 2.x Tool; keep the Tool and selected Core/MDX packages at matching versions. The [upgrade notes](migration-2.0.md) explain dependencies, static versus trusted project inspection, and Testing updates.

## One definition for both hosts

A site assembly exports exactly one public, nonabstract, nongeneric `ISiteFactory` class with a public
parameterless constructor. The tool compiles the project and loads that factory
in a fresh child process. This reloads C# code and releases DLL locks when each
build ends. Site code runs with the current user's permissions.

```csharp
using LithoSharp;
using LithoSharp.Configuration;
using LithoSharp.Content;

public sealed class SiteFactory : ISiteFactory
{
    public async Task<SiteDefinition> CreateAsync(
        SiteFactoryContext context, CancellationToken cancellationToken = default)
    {
        var posts = await new MarkdownPostReader().ReadAllAsync(
            Path.Combine(context.ProjectDirectory, "content"));
        return new SiteDefinition(new SiteSettings
        {
            Title = "My docs", BaseUrl = "https://example.com/", TimeZone = "UTC"
        }, posts) { OutputDirectory = "dist" };
    }
}
```

A regular console program can call the same factory:

```csharp
var root = Environment.CurrentDirectory;
var definition = await new SiteFactory().CreateAsync(new SiteFactoryContext(root));
var result = await new SiteGenerator().GenerateWithOptionsAsync(
    definition.Site, definition.Posts, Path.GetFullPath(definition.OutputDirectory, root),
    false, definition.Customization, definition.Options, CancellationToken.None);
```

Use `context.ProjectDirectory` for source paths; `AppContext.BaseDirectory` belongs
to the host process. A relative `SiteDefinition.OutputDirectory` is relative to the
site project. CLI `-o` is relative to the shell's working directory. `Customization`
and `Options` are the ordinary library objects, including collections, layouts,
assets, quality thresholds, timestamp, and cache policy. Set a reproducible timestamp
when comparing generated bytes; see [incremental builds](incremental-builds.md).

## Commands

| Command | Behavior |
| --- | --- |
| `new docs\|blog\|empty\|mdx` | Invokes the installed project template. |
| `capabilities --format json` | Reports this Tool's Core identity, contracts and capabilities without evaluating a project. |
| `markdown-compat <file> --advisory on\|off` | Inspects an explicit Markdown file using the same syntax analysis as editor inspection; optional `--project <snapshot.json>` supplies context data without compiling a project. |
| `preflight --mode static --input <file>` | Inspects explicit source inputs without MSBuild or a factory. MDX needs a restored analysis worker. |
| `preflight <project> --mode trusted` | Compiles and runs trusted factory/catalog code without rendering or publishing; optional `--input` checks explicit sources. Coverage remains `Partial`. |
| `build [project]` | Compiles and generates incrementally; `--clean` requests a full replacement build. |
| `serve [project]` | Builds, watches, and serves on loopback; `--port` selects a port. |
| `check [project]` | Generates in temporary output and runs quality validation without publishing the configured output. |
| `check-output --output <directory> --base-url <url>` | Reads existing output without compiling or regenerating; see [output inspection](generated-output-checks.md). |
| `clean [project]` | Removes unchanged owned artifacts using the library's ownership verification. Caches are never removed by `clean`. |
| `cache info\|clean -o <directory>` | Explicitly reports or removes the incremental cache partition of one output (`--cache-dir` for a custom cache root). Never runs as part of a build and never removes the published output or another output's partition. |
| `inspect [project]` | Refreshes the site, then shows its build graph, output paths, owners, and actual cache hits/miss reasons. |
| `restore-mdx <worker>` | Restores the MDX worker's locked npm dependencies explicitly. |
| `snapshot <source> <destination> <version>` | Creates a versioned documentation snapshot in a separate destination. |
| `extract-translations <source>` | Reports translation keys from supported source files as JSON without changing those files. |
| `migrate testing --dry-run --source <file.cs> --reference <legacy.dll>` | Reports legacy Testing reads using explicit source and PE metadata; never edits files or executes the supplied assemblies. See the [migration map](Testing-v2-api.md#migration). |
| `migrate docusaurus <source>` | Analyzes a Docusaurus site without executing its JavaScript configuration. With `--output <directory>` it converts into a separate directory and never overwrites the input. `--expected-routes <file>` compares routes exactly; a classified oracle plus `--compare-normalized-pages` opts into a separate normalized document-page comparison. `--base-url` and `--default-locale` set migration assumptions. See the [Docusaurus migration guide](docusaurus-migration.md). |

Select a project file or a directory containing one project. `-c Release` changes
the build configuration. `check --format text|json|sarif` uses the library's diagnostic
formatter; `inspect --format json` provides structured graph and cache information.
Compilation errors and ambiguous projects fail the command; factory/loading and
site validation failures are reported rather than publishing incomplete output.

Static inspection, trusted preflight, generation and output inspection answer
different questions. A source-only result has no project-bound route/schema
proof. Trusted preflight does not render final HTML; `check` regenerates a
temporary site; `check-output` reads existing bytes and does not prove source
freshness. Custom C# schema validation belongs to compilation/site builds, not
the language-server's built-in-schema snapshots. See [the complete preflight
contract](../src/LithoSharp.Tool/README.md#preflight).

`serve` watches project files, debounces changes, and excludes build output and
caches. Content changes use incremental generation; C# and project changes also
recompile. The browser reload script is injected into HTTP responses, leaving files
on disk unchanged. `/_lithosharp/diagnostics` exposes the current build status, and a
browser overlay shows failed builds. The previous committed output remains available
when a rebuild fails. Changes outside the watched project directory require a restart.

In JSON mode, `POST /_lithosharp/watch-barrier` waits up to 60 seconds for already
admitted watch inputs and their builds to finish. It returns a fixed generation,
owner and host identity, not a promise that no later native events can arrive.
Rebuild terminals include a `watch` witness with consumed restart reasons,
input revision and previous/current host. Recovery events are distinct from
ordinary host reuse. Integrations should consume the structured fields rather
than infer successful reuse from logs or the absence of a restart message.

`SiteGenerator.CleanAsync(outputDirectory, cancellationToken)` returns removed
relative paths. Modified and unowned files remain. Ownership metadata is required;
an output manifest alone cannot authorize deletion. Filesystem roots and unsafe
reparse paths are rejected. Cancellation before commit preserves previous output.
`build --clean` retains its existing full-replacement semantics and differs from
this selective `clean` command. Caches are not deletion authority and are not removed
by `clean`.

## Structured output and 1.x compatibility

`build`, `check`, `inspect`, `migrate` and the development server expose
machine-readable results. Successful and failed JSON carries `schemaVersion`
(currently `"1.0"`) with a stable envelope; unknown fields are ignored so that
additive extensions keep working. Exit codes are `0` for success, `1` for
failure, `2` for usage errors, `3` when Docusaurus migration includes unsupported
content, and `130` for cancellation.
Ordinary project compilation failures also return `2`; trusted preflight captures
compiler failures inside its phase report and returns `1`. Check the command's
report rather than treating every nonzero result as the same failure class.
Manual-action findings remain in the report and do not by themselves change exit `0`.
The development server emits one JSON object per line for
startup, rebuilds and shutdown. Diagnostic codes, inspection shapes and the
migration report retain the documented additive 1.x contract. The current 2.x behavior and Testing API migration are described in the [upgrade notes](migration-2.0.md); a package major version is not the same as the structured-output schema version.

## Troubleshooting

- Port already in use: `serve` reports a structured startup failure and exits
  without guessing another port. Pick a free `--port`.
- Missing Node.js: Markdown-only sites build without Node. MDX builds fail with
  `LSMDX002` naming the configured executable; install Node.js 24.13.0 and
  restore the worker dependencies.
- Unrestored dependencies: run `dotnet restore --locked-mode` for .NET and
  `restore-mdx` (or `npm ci --ignore-scripts --no-audit --no-fund` in the
  worker directory) for MDX before building.
- Worker toolchain drift: the build rejects Node, MDX, React or esbuild
  versions outside the locked set instead of bundling with them.
- Strict front matter and route collisions fail the build with positioned
  diagnostics; fix the content rather than the output.

## Distribution boundaries

The supported distribution is the framework-dependent .NET tool. Single-file
publishing is evaluated separately from tool packing. The host loads an external
site assembly; bundling the tool cannot bundle an arbitrary future site.

Trimming and Native AOT are not supported for this dynamic site host. Runtime factory
discovery and arbitrary site dependencies cannot be analyzed when publishing the
tool. Native AOT does not support loading arbitrary managed assemblies. These are
explicit boundaries, not promises of compatibility based on an untested flag.
