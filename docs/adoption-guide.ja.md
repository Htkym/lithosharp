# LithoSharpの導入を判断する

[English](adoption-guide.md)

LithoSharpは、製品ドキュメント、手書きの技術ガイド、構造化したナレッジサイトを
管理する.NETチームを主な対象としています。C#のコンテンツ型、生成した参照、
コンパイル診断、生成物の検査を、同じビルドの流れで利用できます。
このガイドでは適合条件と評価方法を示します。製品の順位や工数の削減率は示しません。

## 適合条件と運用の負担

サイト全体を移行する前に、代表的なDocsの小さな区画で試してください。
.NET 10のプロジェクト、C#のfront matter型、ルート宣言を管理し、CIでコンパイルと
生成の診断を確認する担当者が必要です。Markdownの執筆者がC#を書く必要はありませんが、
スキーマ、レイアウト、ビルドの変更にはC#の知識が必要です。
新規Docsテンプレートには型付きの構成が含まれます。
[Quick Start](quickstart.ja.md)と[Docsの設定](docs-template.ja.md)を参照してください。

MarkdownだけならNode.jsとReactは不要です。任意で導入するMDXには、固定された
Node.jsとworkerの依存関係を用意し、明示的にworkerを復元します。
サイトのfactory、MSBuildのタスク、MDXは信頼するビルドコードとして実行します。
HTMLの検査はコードのsandboxではありません。配布するのは生成した静的ファイルです。

現在の生成器の執筆方法、プラグイン、配置手順が用途に合い、スキーマ、ルート、
コンポーネントを変更する理由がなければ、その構成を維持する選択もできます。
既存URL、ナビゲーション、独自のMarkdownやMDX構文、テーマとCSS、CIの挙動は
それぞれ確認してください。入力を変換できても、すべての挙動が互換とは限りません。
[移行手順](migration-2.0.ja.md)と[制約](known-limitations.ja.md)も確認してください。

## 用途と既存資産から選ぶ

| 既存資産・用途 | 判断する内容 |
| --- | --- |
| Astroのコンポーネントとコンテンツ中心のWebサイト | Astroを続ければ、そのWeb・コンポーネントの構成を維持できます。C#のコンテンツ型と.NETビルドへの接続が必要なら、LithoSharpを評価し、コンポーネントと設定の変更を確認してください。 |
| Starlightのドキュメントサイト | StarlightはAstroの文書向け構成を使います。現在のサイドバー、テーマ、検索、連携機能を、LithoSharpのDocs機能でどう扱うかを確認してください。 |
| React・MDXのプラグインとバージョン別文書を持つDocusaurus | 現在のプラグインとコンポーネントの資産を確認してください。LithoSharpには任意のMDX機能と限定的な[移行手順](docusaurus-migration.ja.md)があります。任意のプラグイン、JavaScript設定、Reactの挙動が自動で移るわけではありません。 |
| DocFXと.NET APIリファレンスの資産 | APIリファレンスを中心とした既存の運用にはDocFXが合う場合があります。LithoSharpでは型付きの手書きガイドとXML .NET API・OpenAPI入力を組み合わせられます。必要なリファレンスとxrefの出力を実際の入力で確認してください。 |
| Statiqのパイプラインと独自C#処理 | 現在のパイプラインを維持する価値を確認してください。必要な処理と拡張の挙動を、LithoSharpのサイト・コンテンツAPI、生成参照、出力確定前の検査でどう扱うかを評価します。 |

この表は用途の確認事項であり、性能や機能の完全な同等性を示すものではありません。
[性能の根拠](performance.ja.md)は、記載されたバージョン、入力、測定区間、環境の範囲で
参照してください。測定値から移行の工数は推定できません。

## 自己利用の記録：DocsSample

リポジトリの[DocsSample](../samples/LithoSharp.DocsSample/README.ja.md)は、製品の
利用例と検証用の入力として保守しています。自己利用の根拠であり、独立した外部利用や
本番導入の事例ではありません。

| 記録項目 | 実装または再現できる例 |
| --- | --- |
| 利用条件と課題 | リポジトリ内の.NET Docsサイトで、Markdownのメタデータ、C#の参照、Docsナビゲーション、生成HTMLの整合性を確認します。 |
| 採用した契約 | `ArticleFrontMatter`、生成Binder・Catalog、型付き参照で、宣言したコンパイル入力と実行時loaderを接続します。実行手順と分離した異常例はサンプルのREADMEにあります。 |
| 検出できる問題 | 必須タイトルの欠落はコンパイル時の`LSG006`、確定したentryとルートの矛盾はAnalyzerの`LSA1402`、出力のリンク先・anchorの欠落は品質検査の`LSQ001`・`LSQ002`で確認します。本番で防いだ問題の件数ではなく、制御された例です。 |
| 生成物の検査 | サンプルをビルドまたは実行し、実際のHTMLとルートを調べ、体験手順の出力検査を実行します。評価時にはソースのrevisionとコマンドの結果を記録してください。 |
| 導入時の判断 | コンパイル入力のrootと除外を実行時loaderにそろえ、必須項目とルートの規則を移行時に決めます。 |
| 残る制約 | 動的な参照や、エディターで取得できないcontextは未確定です。出力検査は原稿の最新性や外部HTTPの応答を保証しません。エディターは入力のたびに独自スキーマを実行しません。 |

この記録はサンプルと検査内容の説明です。新しい性能測定、外部利用者の感想、本番規模の
利用実績を示すものではありません。

## 外部評価の準備

参加者と外部リポジトリは未指定です。以下の依頼文案と記録様式は、対象と許可範囲を
決めた後の評価に使えます。この文書だけを根拠として連絡、他リポジトリの改修、
事例の公開は行いません。

試す対象には、必須項目、型付きのページ間参照、維持したい既存URL、独自レイアウトの
リンクを含む、小さな.NET製品ドキュメントを選んでください。Markdownから始め、用途に
必要な場合だけMDXを加えます。Quick Startの後に、DocsSampleの分離された異常例を
試してください。迷った操作や実行しなかった検査も、実際の結果として記録します。
常時telemetryの導入は前提にしません。

### 依頼文案

> .NET製品ドキュメントの小さな区画で、LithoSharpを試していただけますか。
> C#のコンテンツ型、生成参照、Docs表示、ビルドと生成物の診断を評価するための依頼です。
> Quick Startに沿って操作し、環境、試した手順、検出できた問題、分かりにくい点や
> 不足している挙動を、下の様式に記録してください。試行では既存URLを維持してください。
> 秘密情報や無関係な個人情報は含めないでください。感想の提供だけで、お名前、
> リポジトリ、結果の公開を許可したことにはなりません。公開可能な範囲は別途確認します。

送信前に、依頼先、候補パッケージとfeed、参照できるソース、公開可能範囲を決めてください。
この案には期限や参加の約束を含めていません。

### 評価結果の記録様式

自己利用と外部評価で同じ様式を使います。不明な項目は不明、試さなかった手順は未実行と
記載してください。

| 項目 | 実際の試行から記入する内容 |
| --- | --- |
| 根拠の種類と日付 | 自己利用または外部評価、実施日、ソースのrevision・固定パッケージバージョン。 |
| 利用条件 | 文書の種類、関連する既存資産、環境、Markdown・MDXの依存関係、CIの制約。 |
| 解決したい問題 | 具体的な整合性の問題や移行の条件。 |
| 採用したスキーマと参照 | 必須項目、コンパイル入力のroot・glob・除外、entry ID、生成参照、ルート規則。 |
| 操作と結果 | コマンド、終了結果、工程と位置を含む診断、出力検査、根拠へのリンク。未実行・不完全・成功を区別します。 |
| 維持・変更した挙動 | 既存URL、ナビゲーション、部品・レイアウトの挙動、配布する出力。 |
| 導入時の迷い | 判断が必要だった手順、説明、依存関係。 |
| 残る不足 | 再現方法、影響、分類。分類は製品説明、導入、編集、生成、互換性、性能から選びます。 |
| 公開可能範囲 | 閲覧できる人と引用できる内容。公開前に別途許可を得てください。 |

## 根拠に基づく次の確認

| 優先する時点 | 現在の確認事項・不足 | 次に必要な根拠 |
| --- | --- | --- |
| 導入前 | 実際のスキーマ、ルート、必要なナビゲーションを維持できるか。 | 代表的な区画を移行し、生成物を検査します。プロジェクトを上書きせず、移行ガイドに従います。 |
| 編集支援に頼る前 | 現在の編集中に、原稿とプロジェクトのどの情報を検査できるか。 | エディターが示すcontext・coverageと、独自スキーマのコンパイル・ビルド結果を確認します。 |
| 性能で判断する前 | 測定した入力が、予定するDocs・Quality・MDXの用途に合うか。 | [測定の根拠](performance.ja.md)を確認し、必要に応じて実際の入力で再現可能な測定を行います。未測定の速度や工数削減は記録しません。 |
| 試行後 | 次に何を改修するか。 | 再現方法と影響を含む評価結果を記録します。この記録には外部評価の結果はまだありません。 |

大規模な最適化、入力ごとのスキーマ実行、未保存文書のフルプレビューを提案する前に、
様式に沿って不足を分類してください。評価参加者が未定でも、独立して検証できる製品改修は
進められます。
