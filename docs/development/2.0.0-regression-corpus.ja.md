# 2.0.0の観測corpusと必要な検証

J-02は、既存の小さい入力、観測する期待値、差を許容する条件を固定します。新しいparserやharnessの実装タスクではありません。機械可読の索引は[regression-corpus-v1.json](regression-corpus-v1.json)で、両repoに同一bytesを置きます。各参照には基準commit、source path、Git blob ID、blob bytesのSHA256を記録します。fixtureディレクトリはGit tree IDで固定し、巨大な入力やsnapshotを複製しません。

基準はLithoSharp `9317af45a7bf8b08b000b693d27fbe33406db7a6`、SharpDeps `e16985d01c1e8e5f4bc1a530f84389ba308b1545`です。いずれもJ-01の契約文書を含むfeature branchのcommitです。J-01の契約例は机上の期待値で、実parserの合格結果としては扱いません。

## 旧oracleの境界と差の扱い

Markdigはすでに製品と別の `tests/LithoSharp.MarkdigComparison` projectにあります。ロックファイルのresolved版は1.4.0で、package content hashも索引に固定します。通常製品経路のNoMarkdigAssemblyLoadsを保ち、製品への参照を追加しません。後続で参照比較を実行するときは、同じロックの版を使います。

Markdigとの比較はC01の対応済み構文から始めます。既存helperのタグ間空白正規化を超えてtext/URL/位置を曖昧にしません。全Docusaurus比較、巨大文書、pathological入力は毎回の完了条件にしません。現行LithoLimitsで未対応のfootnote等をMarkdigが描画できても、製品の期待値へ昇格させません。一部の比較test commentに残る旧unsupported一覧より、現行LithoLimitsと製品assertionを優先します。

AngleSharpは現行Core/Testingの製品依存として残っています。J-02で撤去したとは記録しません。既存HTML assertionを撤去前の観測基準として使い、将来live oracleが必要な場合だけ、固定版を別test project/processへ置きます。製品や公開packageへoracle参照を戻しません。全DOM構造やserializationの一致を互換条件にはしません。

索引のallowedDeltasは、差を記録するための条件です。IDだけを付けて差を自動承認するものではありません。

| 差 | 許容する範囲と必要な理由 |
| --- | --- |
| 公開IDocument getter | HT-05/IN-02の許可major差分としてsnapshot/queryへ移行。Assertの意味とdispose後拒否を保持し、移行例を添える |
| 新Markdown entry | J-01の任意frontmatter、strict Unicode、raw TextHash/segments。旧inspection診断と旧hashの意味は保持する |
| HTMLの位置/coverage | HT-01で個別に固定。既存text/meta/URL/品質診断の差を無条件に許容しない |
| 新member graph/確定した欠落修正 | 旧report v2の意味を保持。欠落修正は入力、symbol、before/afterの確定根拠をレビューする |
| host固有値/編集による位置移動 | 既存projectionの正規化範囲だけ。入力編集による差は入力変更として記録する |
| 旧oracleとの能力差 | 現行製品の対応範囲・独自renderを根拠に個別説明する |

golden更新flagを先に有効にして差を消しません。期待値を変えるときは、関連task、基準/候補SHA、入力hash、変更した観測、許容理由、review結果をtask証拠に残します。

## 担当AIの確認手順

まずtaskの実差分が触る境界に対応するcaseを選び、既存test runnerのfilter方法を確認します。小さいcaseで具体的な回帰を確認し、失敗や新しい未解決境界がある場合にだけ範囲を広げます。文書だけの変更はJSON読戻し・source/golden照合・diff checkで確認します。build/restoreを伴うcaseは、同PCの計測への影響をBocchiと調整してから実行します。

各task証拠にはcase ID、入力ref/hash、実行commandと終了結果、実際の観測差、未実行理由を記録します。未実行を合格に数えません。既存のCI成功と、変更した実装の確認結果も分けます。新Analyzer hostのRA-01 canaryや新storage/watchの故障確認は担当taskで小さく追加し、この基準corpusに実装済みであるかのように含めません。

J-01末尾の参照先を台帳に合わせ、MD-02へSourceSegments/YAML位置、MD-03へruntime/inspection/site adapter、MD-04へcompiler host/cache/世代を割り当てます。契約内容、task順序、依存を変更する修正ではありません。

## J-02の証拠と停止条件

JSON読戻し、両repoの索引同一性、source blob/hashとfixture tree、実在symbol、task ID、C03/C04の入力/assertion、C05/C06のgolden projection、公開diffの範囲を軽いscriptで確認します。

既存CIはLithoSharp mainの `e6419c202bb95bb0055650bc7f04e0dcd6fe0f29` に対する[run 37594613458](https://github.com/Htkym/lithosharp/actions/runs/37594613458)がWindows/Ubuntu/macOSのTest stepを含めて成功しています。SharpDepsはJ-01の基準SHAに対する[run 37715916248](https://github.com/Htkym/sharpdeps/actions/runs/37715916248)がbuild/macOS smokeおよび既存Quick/Semantic golden検証で成功しています。これらは選んだ全caseの今回の個別実行や、新parser/harnessの動作確認を示すものではありません。

同PCのZendiator計測を優先し、ローカルbuild/test/restore/packは実行しません。J-02のcommit/push後は、実SHA・diff・軽いcheck結果・未実行理由を返し、Bocchiのレビューが通るまで次taskへ進みません。
