# 参照の検査と編集

参照の検査は、明示的に取得したプロジェクトのカタログと、現在のエディターバッファーを使います。
入力中に、プロジェクトのファクトリ、MSBuild、利用者のコードを実行しません。
Markdown の宛先、参照定義、使用箇所、見出しには、Syntamark の構文と正確な UTF-16 の範囲を使います。
コード例やフロントマターの値を文字列検索して、参照に変えることはありません。

言語サーバーは、補完、ホバー、定義、参照、見出しの名前変更、`workspace/willRenameFiles` の準備要求を提供します。
宛先の変更や文書の移動は、`lithosharp/previewRename` でも確認できます。
Markdown の自動処理の範囲は、取得したバッファーです。
閉じた文書、動的な式、利用できない構文、曖昧な参照先、C# の呼び出し側は、明示的なレビューの範囲として残ります。

## カタログの範囲を選ぶ

各ルートは、コレクション、バージョン、言語を保持します。
取得した組に一つだけ一致する場合は、サーバーがソース文書の範囲を選びます。
複数の組に一致する場合は、明示的な選択が必要です。

`lithosharp/referenceScopes` を `{ "textDocument": { "uri": "file:///..." } }` で呼ぶと、
`scopes`、`sourceVersion`、プロジェクトとクライアントの文脈の世代を取得できます。
各範囲は、`collection`、`version`、`locale`、`publicPaths` を含みます。
参照と名前変更の要求は、選んだ組を `referenceScope` として受け付けます。
ソースのバージョンや取得世代が変わったら、選択を破棄してください。

解決結果は、`Resolved`、`Ambiguous`、`Unresolved`、`Unavailable` を区別します。
カタログの根拠の欠落や不完全さは、参照先や参照の不在を証明しません。
別名のルートは補完候補として別に保持します。

## 編集の確認と適用

`lithosharp/previewRename` は、文書、位置、`newName` を受け付けます。
解析したリンクの宛先を変える場合は、`kind` を `target` にします。
文書の移動では、位置の代わりに `newUri` を渡します。任意の `newPublicPath` は、実際のルート変更を宣言します。
サーバーはファイル名から新しい公開 URL を導出しません。

プレビューは、保護付きのテキスト編集、物理ファイルの移動、ソースのバージョンと文字列のハッシュ、
`manualScopes`、`isComplete`、`canApply` を含みます。各テキスト編集は、期待する元の文字列を保持します。
サーバーは、編集を返す前に取得したバッファー全体とバージョンを検証し、応答の送信前にも識別情報を再確認します。
期待する入力が古い場合は拒否します。

標準の編集は、バージョン付きの `documentChanges` を使い、クライアントが対応を宣言する必要があります。
複数文書の変更には、トランザクションを使うテキスト編集への対応が必要です。
残る手動確認の範囲には、確認用の注釈と、それに従うクライアントが必要です。
サーバーは、バージョンのない置換集合を返さず、未対応の適用方法を拒否します。

`workspace/willRenameFiles` は、現在、一度に一つの移動を準備します。
応答は Markdown の参照を更新し、要求したファイルの移動はエディターが行います。
正確なソース対応が編集を許す範囲で、ラベル、前後のタイトル、相対形式やバンドルルート形式、
ソースのエスケープ、改行を維持します。対応が不明、または参照先が曖昧な場合は、手動確認に残します。

C# の確認は、`lithosharp preview-csharp-rename` に、ソースファイル、参照アセンブリ、メタデータの型名、
メンバー名、新しい識別子を明示して、別に行えます。
文書の名前を C# のシンボルと推測しません。生成した C# ファイルは、直接の編集対象ではありません。

## OKF 入力の根拠

OKF は、同じ取得済みのルートと、バンドルリーダーによる関係の分類を使います。
概念、ディレクトリのインデックス、ログ、補助アセットは、異なる入力の種類を保持します。
既存のバンドル外・未解決の関係の判定に従います。
補助ファイルの参照先はバイト列を Markdown として解析せずに解決できます。

入力ポリシーは Markdown 本文のプロファイルとネイティブ YAML のプロファイルとは別です。
明示的な OKF 入力メタデータは、フロントマターのないインデックスやログを許し、概念には必須の文字列 `type` を検査します。
未知の OKF メタデータはネイティブ YAML の構文として保持し、通常の文書 DTO にバインドしません。

既知の入力を変更した後も、静的な入力分類を利用できる場合がありますが、ルート、取得した関係、意味の対象範囲の完全性は破棄します。
保持した分類は参照の完全性を証明しません。ファイル集合やプロジェクトが変わる場合は、明示的な再取得が必要です。
