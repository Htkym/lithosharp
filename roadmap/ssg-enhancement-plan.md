# LithoSharp .NET SSG エンハンス計画

## ビジョン

LithoSharp を、Markdown と C# で高速な静的サイトを構築できる、型安全な .NET SSG へ発展させる。

目指す利用体験は次のとおり。

- Markdown、YAML、JSON、CSV を型付きコンテンツとして読み込める。
- C# でルート、ページ、レイアウト、コンポーネント、ビルド拡張を定義できる。
- 内部リンク、front matter、資産参照をコンパイル時またはビルド時に検証できる。
- 変更された入力と依存する成果物だけを高速に再生成できる。
- 生成物は実行時依存のない静的 HTML と資産であり、任意の静的ホスティングへ配置できる。

Astro の思想は参考にするが、Astro 互換や JavaScript エコシステムの再実装は目的にしない。.NET の型システム、Source Generator、NuGet、CLI、テスト容易性を独自の強みにする。

## 非目標

初期ロードマップでは次を対象外とする。

- Astro、JSX、MDX、npm パッケージとの互換性
- Islands Architecture とクライアント hydration
- SSR、動的 API、常駐アプリケーションサーバー
- 任意の C# を Markdown 内で実行する独自構文
- ブラウザ向け JavaScript バンドラーの内製
- CMS、認証、データベースなどの実行時機能

これらは静的サイト生成の品質を損なわず、利用者の需要と保守可能性を確認できた場合だけ別計画で検討する。

## 計画策定時の基盤

- Markdown の再帰的な読み込みと YAML front matter の解析
- Docs を既定、Blog を選択可能とする組み込みテンプレート
- `ISiteTemplate` による HTML とテキスト資産の生成
- ページ本文、見出し、前後リンク、ナビゲーションツリーを持つ `SiteTemplateContext`
- SEO、Open Graph 画像、RSS、検索インデックス、サイトマップ、favicon、`llms.txt`
- Docs / Blog サンプル、日本語 / 英語 README、TUnit による回帰テスト

現状は `MarkdownPost` とサイト全体を描画するテンプレートが中心である。ページ単位のビルド、型付きコレクション、資産登録、依存関係グラフ、差分ビルド、CLI は未整備である。

## 設計原則

- **静的 HTML を既定にする**: JavaScript がなくても閲覧、ナビゲーション、SEO が成立する。
- **C# を第一級にする**: ページ、レイアウト、コンポーネント、設定、拡張点を型で表現する。
- **Markdown を簡潔に保つ**: 標準 Markdown と YAML front matter を中心にし、独自構文を増やしすぎない。
- **安全な出力を既定にする**: テキスト、属性値、URL、raw HTML を異なる型で扱う。
- **決定的に生成する**: 同じ入力、設定、ビルド時刻から byte-identical な成果物を生成する。
- **成果物の所有者を一意にする**: 各出力パスは常に一つのビルドノードだけが所有する。
- **設定より規約を優先する**: 一般的な構成は設定なしで動き、必要な箇所だけ C# で上書きできる。
- **低レベル API を残す**: 高水準 API で表現できない場合は、検証済みの低レベル出力 API を使える。
- **機能を分離可能にする**: 利用しない機能が依存関係、出力、ビルド時間を増やさない。

## パッケージ構成

公開 API を増やす前に、将来の責務境界を固定する。

- `LithoSharp.Core`: ルート、ページ、ビルドグラフ、HTML、資産、診断
- `LithoSharp.Markdown`: Markdig、YAML front matter、Markdown コレクション
- `LithoSharp.Templates`: Docs / Blog の組み込みレイアウトとコンポーネント
- `LithoSharp.Generators`: Source Generator と Analyzer
- `LithoSharp.Testing`: メモリ生成、HTML、ルート、診断のテスト支援
- `LithoSharp.Images`: 画像変換、WebP / AVIF、レスポンシブ画像
- `LithoSharp.Tool`: `dotnet tool` と開発サーバー
- `LithoSharp`: 初期段階では主要パッケージをまとめる互換メタパッケージ

既存 Blog の検索、RSS、サイトマップは互換性のため維持する。分離後は `LithoSharp.Templates` が必要な機能へ依存し、更新だけで成果物が消えないようにする。

## フェーズ 0: 互換性と測定基盤

目的は、大規模な設計変更の前に現在の動作と性能を固定すること。

### 実装

- Docs / Blog のルート、HTML、canonical、RSS、検索、サイトマップ、資産名をフィクスチャ化する。
- 少量、中規模、大量の固定コンテンツ corpus を追加する。
- クリーンビルド、no-op、単一ページ変更、全体変更のベンチマークを用意する。
- 公開 API の一覧と互換性ポリシーを文書化する。
- 旧 API は新 API の代替が完成した次のメジャー版まで維持する。
- `Obsolete` は移行先、移行例、削除予定バージョンを示せる場合だけ付与する。

### 完了条件

- 現在の全出力パスと主要 HTML 構造を自動テストで検証できる。
- 基準となる時間、ピーク割当量、生成ファイル数を記録できる。
- 破壊的変更を検出する API 互換性チェックを CI で実行できる。

## フェーズ 1A: ルートとページモデル

目的は、すべてのページを共通のルート表で管理すること。

### 実装

- `SiteRoute` を導入し、canonical public URL と相対出力パスを一意に保持する。
- `.html`、`index.html`、末尾スラッシュ、`BaseUrl` のサブパス、Unicode、percent-encoding、大小文字衝突、予約パスの規則を固定する。
- `SitePage<TContent>`、`RenderedPage`、`PageMetadata` を追加する。
- Markdown、C# 定義ページ、追加ページを同じページモデルへ統合する。
- `SiteExtraPage.BodyHtml` は互換 API として維持し、新ページ API へのアダプターを提供する。
- Docs / Blog の既存 URL を選択できる互換ルーティング規約として実装する。
- `draft`、公開日時、公開終了日時、環境別公開条件をページメタデータへ追加する。
- 公開対象外ページが、一覧、検索、RSS、サイトマップ、前後リンクへ混入しないようにする。

### 完了条件

- すべてのリンク、canonical、RSS、検索、サイトマップ、OG 資産が同じルート表を参照する。
- ルート重複、パス逸脱、予約パス、大小文字衝突を明示的な診断として報告できる。
- 既存 Docs / Blog の URL を互換モードで維持できる。
- 下書きと公開予定ページをビルド環境ごとに正しく除外できる。

## フェーズ 1B: ビルドグラフと再現可能性

目的は、差分ビルドを後付けせず、最初から成果物と依存関係をモデル化すること。

### 実装

- `SiteBuildPlan`、`BuildNode`、`BuildInput`、`BuildArtifact` を追加する。
- ページ、CSS、画像、検索、RSS、サイトマップを出力パス、所有者、依存関係付きで宣言する。
- 直接依存、コレクション全体への依存、設定値への依存、ファイル依存を区別する。
- 既存 `ISiteTemplate` は不透明な全体ビルドノードとして扱い、安全のため全再描画する。
- `BuildTimestamp` と clock を注入可能にする。
- `SOURCE_DATE_EPOCH` をサポートし、時刻ベースのキャッシュバスターをコンテンツハッシュへ変更する。
- ビルド計画を検証してから出力を開始し、成果物競合を事前に検出する。

### 完了条件

- 各成果物の所有者と再生成理由を列挙できる。
- ページ本文の変更時に、本文、前後リンク、ナビゲーション、検索など必要なノードだけが無効化される。
- 同じ入力、設定、ビルド時刻による 2 回のクリーンビルドが byte-identical になる。
- 失敗またはキャンセルされたビルドが成功済み成果物を破損しない。

## フェーズ 1C: 型付きコンテンツコレクション

目的は、後続のページとコンポーネント API を型付きコンテンツの上に構築すること。

### 実装

- `ContentCollection<TFrontMatter, TBody>` と `ContentEntry<TFrontMatter, TBody>` を追加する。
- Markdown、YAML、JSON、CSV の組み込みローダーを提供する。
- コレクションごとに入力ルート、ルート規約、レイアウト、並び順、公開条件を設定できるようにする。
- YAML の strict / unknown field、alias、nullability、既定値、scalar 変換、重複 key の方針を固定する。
- スラッグの一意性をルート単位で判定する。資産名には正規化済みルートのハッシュを使用し、同名ファイルによる衝突を防ぐ。
- コレクションからタグ別、年別、カテゴリ別などのページを作る `GeneratePages<T>()` を提供する。
- 外部データを使うローダーには `DependsOnFile`、`DependsOnValue` を要求する。未宣言入力を使う場合はキャッシュ不可にする。

### 完了条件

- C# 利用側は front matter とデータモデルをコンパイル時に型検査できる。
- 入力データはビルド時にファイル、行、列付きで検証される。
- 複数コレクションからページを生成し、型を保ったままレイアウトへ渡せる。
- タグやカテゴリの静的ページを型安全な API で生成できる。

## フェーズ 2A: 安全な HTML と資産参照

目的は、コンポーネント API を公開する前に HTML と資産の境界を固定すること。

### 実装

- `IHtmlContent`、`HtmlText`、`HtmlAttributeValue`、`SiteUrl` を追加する。
- raw HTML は明示的な unsafe ファクトリを通した場合だけ許可する。
- `javascript:` などの危険な URL スキーム、属性注入、不正な相対 URL を拒否する。
- `SiteAsset`、`AssetUrl`、`AssetRegistry` を追加する。
- コンポーネントは物理パスや文字列 URL ではなく、登録済み資産参照を使う。
- 資産のハッシュ付き URL と元ファイルの対応をビルド計画へ登録する。

### 完了条件

- テキスト、属性値、URL、raw HTML の境界を型とテストで保証できる。
- ページとコンポーネントから未登録資産を参照すると診断される。
- BaseUrl がサブパスでもすべてのページ・資産 URL が正しく解決される。

## フェーズ 2B: C# レイアウトとコンポーネント

目的は、文字列連結中心のテンプレートを再利用可能な C# 部品へ置き換えること。

### 実装

- `IPageLayout<TPage>` と `ISiteComponent<TProps>` を追加する。
- head、SEO、ヘッダー、フッター、ナビゲーション、目次、前後リンク、検索フォーム、パンくずを組み込みコンポーネントとして提供する。
- Docs / Blog を新しいページ、レイアウト、コンポーネント API で再実装する。
- 旧 `ISiteTemplate` から新 API を呼び出すアダプターを提供する。
- コンポーネントをファイル出力なしで単体レンダリングできるようにする。
- テーマ変数と CSS クラスの公開契約を最小限に定義する。

### 完了条件

- 利用者がレイアウト 1 クラスと必要なコンポーネントだけで独自サイトを作れる。
- 組み込み Docs / Blog が新 API 上で既存成果物との互換性を維持する。
- コンポーネントを TUnit などから単独検証できる。

## フェーズ 3: Source Generator と型安全リンク

目的は、.NET SSG としての型安全性を開発時に最大化すること。

### 実装

- `LithoSharp.Generators` を追加する。
- コレクション定義から front matter binder、schema、既知ルート、コンテンツ ID を生成する。
- `PageRef<TPage>`、`ContentRef<TEntry>` を生成し、文字列 URL に依存しない内部リンク API を提供する。
- 存在しないページ、重複 ID、無効なルート、型不一致を Roslyn Diagnostic として報告する。
- JSON Schema を任意で出力し、Markdown エディターの補完に利用できるようにする。
- Reflection 実装も残し、AOT / trimming を利用する場合は Source Generator を推奨する。

### 完了条件

- ページの移動や削除で、参照元にコンパイル診断が出る。
- front matter の C# バインダーを生成コードで実行できる。
- Source Generator を使わない既存利用者も従来どおり動作する。
- Analyzer の診断 ID、重大度、抑制方法を文書化できる。

## フェーズ 4: リンク、リダイレクト、サイト品質

目的は、公開前にサイト全体の整合性を検査できるようにすること。

### 実装

- 内部リンク、画像、見出しアンカー、canonical、リダイレクト先をビルド時に検証する。
- 外部リンク検証はネットワークアクセスを伴う任意機能とし、キャッシュとレート制限を設ける。
- 旧 URL から新 URL への静的リダイレクトを生成する。
- リダイレクトのループ、チェーン、競合、存在しない宛先を検出する。
- 未参照ページ、孤立資産、重複タイトル、SEO 不足、空の説明、到達不能ページを診断する。
- 診断をコンソール、JSON、SARIF で出力できるようにする。
- エラー、警告、情報の重大度と、CI で失敗させる閾値を設定可能にする。

### 完了条件

- 壊れた内部リンクと見出しアンカーを公開前に検出できる。
- ページ移動後も旧 URL から安全に誘導できる。
- GitHub Code Scanning などへ診断を取り込める。

## フェーズ 5: 資産パイプラインと画像

目的は、静的資産を高速かつ安全に扱うこと。

### 実装

- `public` ディレクトリのコピーとハッシュ比較を追加する。
- CSS、JavaScript、画像の変換をビルドノードとして登録できる拡張 API を追加する。
- 初期コアはコピー、fingerprint、整合性ハッシュだけを担当する。
- 圧縮、バンドル、画像変換は別パッケージまたは外部ツール連携に分離する。
- `LithoSharp.Images` で画像サイズ、`width` / `height`、WebP / AVIF、`srcset`、遅延読み込みを生成する。
- 画像変換結果を入力ハッシュと変換設定でキャッシュする。
- CSS や HTML 内の資産参照を fingerprint URL へ解決する。

### 完了条件

- 変更のない資産をコピー・変換しない。
- 画像コンポーネントがレイアウトシフトを防ぐ寸法と複数解像度を生成する。
- 外部変換ツールがない環境でもコア機能だけでサイトを生成できる。

## フェーズ 6: 差分ビルドと永続キャッシュ

目的は、大規模サイトの再生成時間を短縮すること。

### 実装

- `.lithosharp` ビルドマニフェストを導入する。
- 入力ファイル、設定、生成器、テンプレート、サイトアセンブリ、資産、宣言済み外部依存の fingerprint を保存する。
- マニフェストと成果物を一時領域で生成し、成功時だけ原子的に確定する。
- 旧マニフェストが所有する削除済み成果物だけを安全に削除する。
- ページごとのストリーミング書込みを行い、サイト全体の HTML をメモリへ保持しない。
- `MaxDegreeOfParallelism` を設定可能にし、並列安全でない拡張を直列実行できるようにする。
- 各ノードのキャッシュヒット、ミス、再生成理由をビルドレポートへ出力する。

### 完了条件

- no-op ビルドではページを再描画しない。
- 単一ページ変更時は依存ノードだけを再生成する。
- 削除、リネーム、レイアウト変更、ナビゲーション変更、失敗、キャンセル後も出力とマニフェストが整合する。
- クリーンビルドと差分ビルドの成果物ハッシュが一致する。

## フェーズ 7: CLI と開発サーバー

目的は、ライブラリ API と同じ動作を使いやすい開発ツールとして提供すること。

### 実装

- C# サイトの起動契約として `ISiteFactory` を定義する。
- `LithoSharp.Tool` がサイトプロジェクトをビルドし、生成されたアセンブリから `ISiteFactory` を解決する。
- `new`、`build`、`serve`、`check`、`clean`、`inspect` コマンドを提供する。
- `dotnet new` で Docs、Blog、空のカスタムサイトを作成できるようにする。
- `serve` はファイル監視、差分ビルド、ブラウザーリロード、診断表示を提供する。
- `inspect` はルート表、ビルドグラフ、成果物所有者、キャッシュ状態を表示する。
- 単一ファイル配布、trimming、AOT 対応を評価する。

### 完了条件

- カスタム C# レイアウトを含むサイトを `build` と `serve` で実行できる。
- CLI を使わずライブラリ API だけでも同じ成果物を生成できる。
- CLI とライブラリの診断、ルート、成果物が一致する。

## フェーズ 8: テスト支援

目的は、サイトと拡張機能を通常の .NET テストとして検証できるようにすること。

### 実装

- `LithoSharp.Testing` を追加する。
- メモリファイルシステムまたは一時出力でサイトを生成する `SiteTestHost` を提供する。
- ルート、HTML、メタデータ、リンク、診断、成果物を検証するアサーション API を提供する。
- コンポーネントとレイアウトの単体レンダリングを支援する。
- HTML 文字列全体に依存しない DOM ベースの検証を提供する。
- 必要に応じて Playwright 連携用のヘルパーを別パッケージで提供する。

### 完了条件

- 利用者が外部プロセスを起動せずに生成サイトをテストできる。
- カスタムコレクション、レイアウト、コンポーネント、ルート規約を単体テストできる。
- Docs / Blog サンプルが公開テスト API の利用例になる。

## フェーズ 9: オプション機能

目的は、コアを肥大化させずに実用機能を追加すること。

- コードシンタックスハイライト
- 全文検索プロバイダー
- RSS / Atom / JSON Feed
- バージョニングされたドキュメント
- i18n とロケール別ルーティング
- パンくず、関連ページ、バックリンク
- Git 情報を使った最終更新日時と著者表示
- デプロイ先別の設定プリセット

各機能は独立した設計提案、性能評価、パッケージ境界を持たせる。コアパッケージは、これらを導入しなくても完全な静的サイトを生成できる状態を維持する。

## 性能目標

固定 corpus と同一マシンの CI ベンチマークで追跡する。

- 小規模: 100 ページ
- 中規模: 1,000 ページ
- 大規模: 10,000 ページ

各規模で次を計測する。

- クリーンビルド時間
- no-op ビルド時間
- 単一ページ変更時間
- 全体レイアウト変更時間
- ピークメモリと割当量
- 再描画ノード数
- キャッシュヒット率

初期の合否基準は現在実装の測定後に決める。以後は、同一 corpus で 10% を超える性能劣化またはメモリ増加を検知し、理由の説明なしには取り込まない。

## セキュリティと信頼性

- 出力先のパス逸脱、シンボリックリンク、大小文字差による競合を防ぐ。
- HTML、属性、URL、raw HTML の境界を型で分離する。
- 外部コマンドは明示的に許可された拡張だけが実行できる。
- ネットワークアクセスを伴う機能は既定で無効にする。
- キャッシュとマニフェストは信頼できない入力として検証する。
- 生成途中の失敗で既存の正常なサイトを破損しない。
- キャンセルを全 I/O と長時間処理へ伝播する。

## API と移行方針

- `SiteGenerator.GenerateAsync`、`MarkdownPostReader`、`SiteCustomization`、`ISiteTemplate` は新 API のアダプターとして維持する。
- 旧 API の代替が完成し、サンプルと移行ガイドを提供した次のメジャー版でのみ削除を検討する。
- 新 API は責務別の名前空間とパッケージへ配置する。
- 各公開型に XML ドキュメント、最小コード例、エラー条件を記載する。
- 各フェーズで API レビューと NuGet パッケージ内容の確認を行う。
- 破壊的変更はリリースノートと移行ガイドに記載し、可能な限り Analyzer で移行を支援する。

## 推奨する実施順

1. フェーズ 0 で互換性と性能を固定する。
2. フェーズ 1A でルートとページモデルを導入する。
3. フェーズ 1B でビルドグラフと再現可能性を導入する。
4. フェーズ 1C で型付きコンテンツコレクションを導入する。
5. フェーズ 2A で安全な HTML と資産参照を導入する。
6. フェーズ 2B で C# レイアウトとコンポーネントを導入する。
7. フェーズ 3 で Source Generator と型安全リンクを追加する。
8. フェーズ 4 でリンク、リダイレクト、品質診断を追加する。
9. フェーズ 5 で資産パイプラインと画像機能を追加する。
10. フェーズ 6 で差分ビルドと永続キャッシュを完成させる。
11. フェーズ 7 で CLI と開発サーバーを提供する。
12. フェーズ 8 で公開テスト支援パッケージを提供する。
13. フェーズ 9 の機能を需要と保守コストに基づいて追加する。

各フェーズは単独でリリース可能なサイズに分割する。次のフェーズへ進む前に、実装、API レビュー、互換テスト、サンプル、英語 / 日本語ドキュメント、性能計測を完了する。
